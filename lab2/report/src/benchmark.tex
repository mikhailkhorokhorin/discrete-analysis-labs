\section{Performance test}

\subsection{Method}

For every size $N$ the generator \texttt{lab2/benchmark/generator.py} produces a set of unique keys
of lowercase English letters with random length from 1 to 16 characters, using a fixed seed. It
writes $N$ insertion commands, then $N$ lookups as plain \texttt{word} lines, then $N$ removal
commands to \texttt{lab2/benchmark/tests.txt}. Three operations are measured separately: insertion
of $N$ keys, lookup of all $N$ keys and removal of all $N$ keys. The program
\texttt{lab2/benchmark/benchmark.cpp} compares \texttt{PatriciaTrie} with \texttt{std::map}, a
balanced search tree from the STL with guaranteed $O(\log n)$ complexity for all operations.

The time of every operation is measured with \texttt{std::chrono::steady\_clock}. Data generation
and input/output are not included in the measurement.

\subsection{Analysis of the results}

On small inputs ($N \leq 10\,000$) \texttt{std::map} is usually faster: the standard
implementation is well optimized, while the overhead of PATRICIA for node allocation, bit checks
and string storage does not pay off yet.

On the medium size ($N = 100\,000$) the results are close: insertion and lookup differ only
slightly, while removal in PATRICIA remains more expensive because of the more complex restoration
of links after a node is deleted.

On large sizes ($N \geq 500\,000$) PATRICIA starts to win: for $N = 500\,000$ all three
operations are faster than in \texttt{std::map}, and for $N = 10^6$ PATRICIA is faster in
insertion and removal. This agrees with the idea of a compressed trie: the
path is determined by the critical bits of the keys rather than by a full lexicographic string
comparison at every level of a balanced tree.
